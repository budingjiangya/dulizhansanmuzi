# 前台导航扩展与站内搜索 · 设计文档

日期：2026-09-27
范围批次：第一批（关于本站 + 搜索；分类与邮件订阅留待第二批）
状态：设计已确认，待实现

## 一、背景与目标

用户要求在访客端顶部导航中新增四个入口：**关于本站、分类、搜索框、邮件订阅**。

经过范围评估，四项涉及四个彼此独立的功能，其中分类与邮件订阅需要新增数据模型、后台管理页与公开写接口，属于独立子系统。因此拆成两批：

| 批次 | 内容 | 是否动数据模型 |
| --- | --- | --- |
| **第一批（本文档）** | 导航栏改造、关于本站页、搜索框与搜索结果页 | 否 |
| 第二批 | 分类（分类字段/表 + 后台管理 + 前台分类页）、邮件订阅（订阅表 + 公开接口 + 后台列表） | 是 |

第一批的目标：

1. 导航结构一次成型，四个入口全部可见（分类与邮件订阅进入「即将上线」占位页，第二批替换为真实页面时不需再改导航）。
2. 站内搜索真实可用：能按关键词搜到已上架文章并进入详情页。
3. 关于本站有真实内容页。

## 二、已确认的决策

| 决策点 | 结论 |
| --- | --- |
| 范围切分 | 分两批，先做「关于本站 + 搜索」 |
| 分类/订阅入口 | 四个入口全放，分类与订阅进「即将上线」占位页（复用 `EmptyState` 视觉语言） |
| 关于本站内容源 | 前端静态页，不新增后端字段 |
| 搜索匹配字段 | 标题 + 摘要 + 富文本正文 |
| 搜索覆盖范围 | 全部**已上架**文章（`isPublish = true`），不限于首页推荐位 |
| 搜索接口形态 | 新增独立端点，不扩展现有首页列表端点 |
| 头部布局 | 桌面单行：站点名+副标题在左，右侧为链接组 + 内联搜索框；窄屏导航换行、搜索框独占一行 |

## 三、方案选择记录

搜索接口有两种做法：

- **方案 1（采纳）**：新增独立端点 `GET /api/portal/articles/search`。首页列表语义固定为「推荐位」，搜索语义固定为「全部已上架」，两者可独立测试与断言，符合仓库现有「一个 controller 一个职责」的组织方式。
- **方案 2（否决）**：扩展现有 `GET /api/portal/articles` 加 `keyword` 参数。端点更少，但首页「只看推荐」会退化为客户端可传的筛选参数，语义边界模糊，且没法再断言「首页一定只返回推荐」。两者排序与可见性规则不同，合并会产生互斥参数。

### 单元边界

- `HeaderSearch` 只做「收集关键词 → 触发提交事件」，不持有搜索结果状态、不直接调用接口。搜索页自行根据 URL 的 `q` 查询。
  这样搜索框可以被别处复用，且搜索结果状态只有一个来源（URL），刷新与分享链接行为一致。
- `SearchView` 只依赖 `route.query.q` 作为唯一输入，路由变化即重新查询。
- `ComingSoonView` 不写死文案，从 `route.meta.title` 读取，一个组件服务两个路由。

## 五、接口设计

```
GET /api/portal/articles/search?keyword=显示器&page=1&pageSize=9
```

- 鉴权：公开（`@Public()`），与其余 portal 接口一致。
- 匹配：`title` / `shortDesc` / `content` 三字段 `contains`，**OR** 关系。
- 可见性：固定 `isPublish = true`。未上架草稿不出现在任何搜索结果中。
- 排序：`sort DESC, updatedAt DESC`，与首页卡片的编辑权重观一致。
- 响应：`PageResult<ArticleListItemVo>`，**不含 `content`**。列表不返回富文本正文，避免把长文本塞进列表响应（与首页列表一致）。
- 入参校验：`keyword` 缺失或 trim 后为空 → `40000`；长度超过 50 字 → `40000`。
- 缓存：**不做 Redis 缓存**。若缓存，每个不同关键词都会产生一个缓存键，污染缓存空间且命中率极低。这也是搜索不能复用首页缓存路径的原因。

契约新增（`contracts/src/domain.ts`）：

```ts
export interface PortalSearchQuery extends PageQuery {
  /** 搜索关键词，必填；匹配标题、摘要与正文 */
  keyword: string
}
```

## 六、页面与交互

### 头部布局

桌面（≥768px）单行：左侧站点名 + 副标题；右侧为「首页 / 全部推荐 / 分类 / 关于本站 / 邮件订阅」五个链接 + 下划线风格的搜索输入框。

窄屏（<768px）：导航换行成独立一行，搜索框独占一行占满宽度。

视觉上延续现有取向：只用留白、字号层级与一条细分隔线，不引入卡片边框、阴影或按钮底色。

### 搜索框行为

- 回车或点击提交 → `router.push({ name: 'search', query: { q } })`。
- 关键词为空（或只含空格）→ 不跳转，焦点留在输入框，不弹错误提示（空提交不是错误）。
- 已经在 `/search` 页面时再次搜索 → `SearchView` 监听 `route.query.q` 变化重新查询，不整页刷新。
- 输入框 `maxlength=50`，与后端校验上限一致。

### 搜索结果页

- 标题区显示「搜索」与当前关键词；提供返回首页入口。
- 结果复用首页卡片组件 `BlogCard`，保持视觉一致。
- 加载中显示骨架屏（复用 `ArticleCardSkeleton`）。
- 无命中显示 `EmptyState`：「没有找到与「xxx」相关的内容」+ 返回首页。
- 有关键词但接口失败显示 `EmptyState` + 重试按钮。

### 占位页

`/category` 与 `/subscribe` 复用 `ComingSoonView.vue`，通过 `route.meta.title` 区分文案（「分类」/「邮件订阅」），内容为「即将上线」说明 + 返回首页入口。

### 关于本站

静态内容页，分节写清：站点定位、评测原则（怎么选品、怎么给结论）、联系方式与投稿说明。排版复用 `.prose-article` 全局样式。

### 可见性规则对齐（规划阶段发现的 spec 矛盾，必须一并处理）

写实现计划时核对代码发现一处内部矛盾：

- `BlogService.findPortalArticleDetail()` 当前要求 **`isPublish && isRecommend`** 才返回文章，否则抛 `40400`。
- 而本设计选定的搜索范围是「全部**已上架**文章」（`isPublish = true`）。

两者直接冲突：搜索会返回「已上架但未推荐」的文章，用户点进去却得到 404，表现为「搜到了但打不开」。

**处理方式**：把详情接口的可见性规则对齐为「**上架即可见**」，即 `findPortalArticleDetail()` 只校验 `isPublish`，不再要求 `isRecommend`。

理由：

1. `isPublish` 在后台的语义就是「上架 / 下架」，`isRecommend` 的语义是「是否出现在首页推荐位」。推荐位是**展示位置**，不应兼任**访问权限**。
2. 首页推荐列表 `findPortalArticles()` 的规则（`isRecommend && isPublish`）**保持不变**——首页仍然只展示推荐位文章。
3. 不这样改，就无法在不破坏点击链路的前提下实现用户选定的搜索范围。

影响面：已上架但未推荐的文章，从此可通过直接 URL 访问（此前会 404）。这是符合字段语义的修正，不是放宽限制。**该改动需要在更新记录中明确标注为行为变更。**


## 七、错误处理与边界

| 场景 | 期望行为 |
| --- | --- |
| 关键词为空或只含空格 | 前端不跳转；后端被直连调用时返回 `40000` |
| 关键词超过 50 字 | 前端 `maxlength` 限制；后端二次校验返回 `40000` |
| 无命中结果 | 结果页空态，文案包含用户输入的关键词 |
| 后端不可用 | 复用现有 `BizError` 提示与重试入口，不白屏 |
| 搜索结果含未上架文章 | 不允许。接口固定 `isPublish = true`，需有断言覆盖 |
| 已上架但未推荐的文章 | 搜索结果中**会**出现，且点击后详情页必须能打开（依赖上文「可见性规则对齐」） |
| 未上架文章的直接 URL | 仍返回 `40400`，前端显示「这篇文章不存在，或者已经下架了」 |
| 关键词含 HTML 标签 | 不进入 `v-html`，仅作为文本插值显示，不存在注入面 |

## 八、验证方式

### 新增 `scripts/verify-search-ui.mjs`（无头 Chrome，与现有三套同规格）

断言：

1. 头部五个入口全部渲染（首页 / 全部推荐 / 分类 / 关于本站 / 邮件订阅）。
2. 搜索框输入关键词并回车 → 跳转 `/search?q=...`。
3. 首屏渲染出的结果卡片数量与搜索接口返回的 `list` 长度一致（排序也需一致：按 `sort DESC, updatedAt DESC` 逐项比对首条）。
4. 结果卡片标题与接口返回一致。
5. 搜索一个必然无命中的关键词 → 显示空态且文案包含该关键词。
6. 点击结果卡片 → 进入 `/article/:id` 详情页并渲染正文。
7. `/category`、`/subscribe` 占位页可访问且显示对应标题。
8. `/about` 页面渲染成功且有正文。
9. 搜索结果不包含未上架文章（先通过后台接口把某篇文章下架，再断言其不出现在搜索结果中，最后恢复上架）。
10. **可见性对齐回归**：把某篇文章设为「已上架 + 取消推荐」，断言它 ① 不出现在首页列表、② 能被搜索命中、③ 详情页可直接打开；完成后恢复推荐位。
11. 控制台无错误、无真实失败请求。

### `scripts/smoke.ps1` 扩容

新增搜索端点断言：

1. 正常关键词命中（`code=0` 且 `total >= 1`）。
2. 结果项不含 `content` 字段（列表轻量化）。
3. 保证不含未上架文章（下架一篇后搜索、断言不出现、再恢复）。
4. 空关键词 → `40000`。
5. 不存在关键词 → `code=0` 且 `total=0`（不是错误）。
6. **详情可见性**：未上架文章的直接 URL → `40400`；已上架未推荐文章的直接 URL → `code=0`（对齐后的规则）。

### 缓存影响

导航项来自后端 `site-config`，该配置有 24 小时 Redis 缓存。改动上线后必须执行 `pnpm backend:cache:flush`，否则前台仍渲染旧导航。此步骤需实际执行并在验证中确认新导航已生效。

## 九、已知限制（明示，不计入已完成）

1. **正文用 `LIKE '%kw%'` 匹配，无法使用索引**。当前内容量下无性能问题；内容规模上来后需改用 MySQL 全文索引（`FULLTEXT` + `MATCH ... AGAINST`）或外部搜索引擎。此为设计取舍，不是待修缺陷。
2. **不做相关性排序**。结果按编辑权重 `sort` 与更新时间排序，标题命中未必排在正文命中之前。
3. **不做关键词高亮**。高亮需要在已渲染 HTML 上做字符串替换，容易引入 XSS 风险，本批次不做。
4. **搜索无防刷与限流**。公开只读端点，本批次不引入 Redis 限流；若后续发现被滥用再补。
